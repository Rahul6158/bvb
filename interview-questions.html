2. Web Scraping & API Reverse Engineering 7 Questions

Q2. "Suppose I give you a website. How would you extract data from it?"

Answer:
First, I would understand what data we need and inspect the website manually.

Then I would check whether the required data is present directly in the HTML or whether it is loaded dynamically through an API.

I would open the browser's developer tools and inspect the Network tab while interacting with the website. If I find an API returning structured JSON, I would generally prefer calling that API directly instead of using browser automation.

If the data is rendered through JavaScript and there isn't a usable API, I would consider Playwright or Selenium.

After extracting the data, I would validate the fields, handle missing or malformed values, deduplicate records, and store the structured output.

Finally, I would add retries, logging, monitoring and failure handling depending on the scale of the system.

Why: The Data Extraction Engineer role explicitly emphasizes website dynamics, scraping/parsing systems, structured data, databases, scalable extraction and debugging website behavior.

Q3. "How do you decide between Requests and Selenium/Playwright?"

Answer:
My first preference is always direct HTTP requests if they are sufficient.

Requests are faster, consume fewer resources, and are easier to scale because I don't need to maintain a browser instance.

I would use Playwright or Selenium when the website depends heavily on JavaScript, browser-generated state, dynamic rendering, or interactions that are difficult to reproduce through direct HTTP requests.

So basically, I don't choose browser automation by default. I first try to understand how the website works and use the lightest approach that reliably gets the required data.

Follow-up they may ask: "Why not always use Selenium?"
Answer: Because running browsers is significantly heavier. If I need to process millions of records, browser-based extraction can become expensive in terms of CPU, memory and execution time. If an API can provide the same information, direct HTTP is usually much more efficient.

Q6. "How do you find an API behind a website?"

Answer:
I usually start with Chrome DevTools and open the Network tab.

Then I perform the action that loads the data — for example searching for a product or moving to the next page.

I filter the requests by Fetch/XHR and inspect the requests that return JSON or other structured data.

I look at the URL, HTTP method, query parameters, request body, headers, cookies and response.

Then I try to reproduce that request outside the browser using Python, initially keeping the important headers, parameters and session information.

Once I can reproduce it reliably, I can build the extraction logic around that endpoint.

Interview Insight: Recent D.E. Shaw reports describe live endpoint-chain reverse engineering and finding changing payload parameters behind dashboard/store-locator pages.

Q7. "What is the difference between GET and POST?"

Answer:
GET is generally used for retrieving resources, while POST is generally used for submitting data or triggering an operation.

GET parameters are commonly placed in the URL, while POST data is commonly sent in the request body.

GET requests are generally intended to be safe and cacheable, whereas POST is typically used when the request changes state or requires a larger structured payload.

Q9. "What is BeautifulSoup?"

Answer:
BeautifulSoup is an HTML and XML parsing library in Python.

It doesn't itself download the webpage. We normally use something like requests to retrieve the HTML and then BeautifulSoup to parse it.

We can use CSS selectors, tags, attributes and other methods to locate the required elements.

Follow-up: "BeautifulSoup vs Selenium?"
Answer: BeautifulSoup is primarily a parser, while Selenium is a browser automation tool. BeautifulSoup works well when I already have the HTML and the required data is available in it. Selenium is useful when browser execution or interaction is required.

Q10. "How do you handle a website where the HTML doesn't contain the data?"

Answer:
I wouldn't immediately assume scraping is impossible.

First I'd inspect the network calls made when the page loads. Usually, dynamically rendered data is coming from an API or another backend endpoint.

If I can identify that endpoint, I'd extract directly from it.

If the data depends on browser execution and can't easily be reproduced through HTTP, I'd use Playwright or Selenium.

Q11. "How would you scrape 10,000 pages?"

Answer:
First I'd understand the pagination mechanism.

It could be page numbers, offset/limit, cursors, tokens, or an API parameter.

If it's a simple API, I'd iterate through the pages using requests and process each response.

For a large workload, I wouldn't necessarily process everything sequentially. I could divide the work into independent jobs and distribute them through something like SQS.

I'd also introduce controlled concurrency, retries with backoff, deduplication and checkpointing so that if a worker fails, I don't lose all the progress.

3. Networking, HTTP, TLS & Anti-Bot Evasion 5 Questions

Q4. "Explain what happens when you enter a URL in a browser."

Answer:
First, the browser resolves the domain name to an IP address using DNS.

Then it establishes a TCP connection with the server. If it's HTTPS, there is also a TLS handshake.

After that, the browser sends an HTTP request containing things like the method, URL, headers and possibly a body.

The server processes the request and sends an HTTP response containing a status code, headers and the response body.

The browser then processes the response. If it's HTML, it parses it and may make additional requests for JavaScript, CSS, images or APIs.

Follow-up: "What is the difference between HTTP and HTTPS?"
Answer: HTTPS is HTTP over TLS. TLS provides encryption, server authentication and integrity for the communication.

Q5. "What are the important HTTP status codes you know?"

Answer:
200: Successful response.
201: Resource successfully created.
301 / 302: Redirects (permanent / temporary).
400: Bad request.
401: Authentication required or failed.
403: Forbidden — server understood but refuses.
404: Resource not found.
429: Too many requests (rate limiting).
500: Internal server error.
502 / 503: Bad gateway / service unavailable (upstream issues).

Then they may ask: "What would you do with a 429?"
Answer: I wouldn't immediately retry aggressively. I'd use backoff, respect rate limits, potentially reduce concurrency, and retry after an appropriate delay if the system allows it.

Q8. "Why did you use curl_cffi instead of requests?"

Answer:
One reason was that some protected websites were sensitive to the TLS characteristics of the client.

Standard Python requests doesn't behave exactly like a real browser at the TLS and HTTP fingerprinting level.

curl_cffi allows us to make requests with browser-like TLS fingerprints, which helped in cases where a normal requests client was being detected or blocked.

I used it specifically where the target's anti-bot system was sensitive to those characteristics.

Likely follow-up: "What is TLS fingerprinting?"
Answer: A server can observe characteristics of a client's TLS handshake — such as supported cipher suites, extensions and their ordering — and use those characteristics as part of identifying the client. A TLS fingerprint (e.g. JA3) is essentially a representation of those characteristics.

Q34. "What are some common ways websites detect automated clients?"

Answer:
There are several signals:

1. Request frequency, burst patterns, and behavioral anomalies.
2. IP reputation, datacenter vs residential IP ranges.
3. Headers (User-Agent, Sec-CH-UA, Accept-Language, Referer) consistency.
4. Cookies, session validation, and CSRF tokens.
5. Browser execution characteristics (navigator.webdriver flags, canvas/webgl fingerprints).
6. TLS characteristics (JA3/JA4 fingerprints, cipher suite order, HTTP/2 frames).

In my work, I've dealt with TLS fingerprinting, browser automation detection and session/token-related behavior.

Q35. "You mention Frida and mitmproxy. Why did you use them?"

Answer:
Some mobile applications don't expose their backend APIs directly in an obvious way.

We used traffic interception to understand the communication between the application and its backend.

Tools like mitmproxy helped inspect network traffic where possible, while Frida could be used to instrument application behavior at runtime.

This helped us understand things like API signatures, request construction and dynamically generated headers (bypassing SSL pinning with Frida scripts and Magisk).

4. Cloud Infrastructure, AWS & Distributed Systems 8 Questions

Q14. "Why did you use SQS?"

Answer:
We used SQS to decouple job submission from job processing.

Instead of the API directly performing the extraction, the API could create a job and put it into an SQS queue.

Workers then consume jobs independently.

This gives us better scalability because we can increase the number of workers based on workload. It also provides buffering when there are more jobs than workers can process immediately.

Q15. "What is visibility timeout in SQS?"

Answer:
When a worker receives a message from SQS, the message isn't immediately deleted. It becomes temporarily invisible to other consumers for the visibility-timeout period.

The worker is expected to process the message and delete it before the timeout expires.

If it doesn't delete the message before the timeout, the message can become visible again and another worker may process it.

In our case, incorrect visibility-timeout behavior contributed to duplicate processing, so we had to investigate the relationship between processing time, visibility timeout and our Redis locking mechanism.

Key Resume Connection: Your resume explicitly highlights solving the SQS visibility-timeout root cause producing duplicate tasks.

Q16. "Why did you use Redis?"

Answer:
We used Redis for fast in-memory operations, particularly for distributed locking and some monitoring-related functionality.

For example, when multiple workers could potentially process the same task, Redis locks helped coordinate access and prevent duplicate processing.

We also used Redis TimeSeries for monitoring pipeline metrics.

Q17. "What is a distributed lock?"

Answer:
A distributed lock is a mechanism that allows multiple processes or machines to coordinate access to a shared resource.

For example, if two workers receive the same logical task, they can both attempt to process it. A distributed lock allows one worker to acquire the lock while the other waits or skips processing.

The important parts are correct lock acquisition (SET resource_name my_random_value NX PX 30000), expiration/TTL, ownership verification during release (Lua script), and safe renewal.

5. Databases, SQL & Data Pipelines (ETL) 6 Questions

Q20. "Suppose you have employees and departments. Explain INNER JOIN vs LEFT JOIN."

Answer:
INNER JOIN: returns only records where there is a match in both tables.
LEFT JOIN: returns every record from the left table, and matching records from the right table. If there is no match, the right-side columns are NULL.

Prepare these SQL topics thoroughly:
INNER JOIN, LEFT JOIN, RIGHT JOIN, FULL OUTER JOIN, GROUP BY, HAVING, WHERE, Subqueries, CTEs, Window functions (ROW_NUMBER, RANK, DENSE_RANK).

Q21. "Difference between RANK and ROW_NUMBER?"

Answer:
Suppose salaries are: 100, 100, 90

ROW_NUMBER() gives: 1, 2, 3
RANK() gives: 1, 1, 3
DENSE_RANK() gives: 1, 1, 2

Conclusion: ROW_NUMBER() gives every row a unique sequential number, while RANK() gives equal values the same rank and leaves gaps after ties.

Q28. "Explain ETL using your scraping system."

Answer:
In my case, extraction is the first step: we extract raw information from the source.
Then we Transform it — parsing fields, converting types, cleaning values, validating records and removing duplicates.
Finally, we Load the processed data into a database such as PostgreSQL or MongoDB.

So the scraping pipeline can essentially be viewed as an ETL pipeline where the external website is the source.

Q29. "Why did you use PostgreSQL and MongoDB?"

Answer:
PostgreSQL: Useful when the data has a structured relational model and we need strong querying capabilities, relationships and ACID transactional guarantees.
MongoDB: Useful when the response structure is more flexible, nested, or when we want to store raw or semi-structured extraction results without rigid migrations.

In our systems, PostgreSQL was used for structured operational data while MongoDB was used for raw responses or flexible catalog data.

Q30. "How would you optimize a slow SQL query?"

Answer:
1. First inspect the query and understand the execution plan using EXPLAIN ANALYZE.
2. Check whether appropriate indexes (B-tree, composite, partial) exist for columns used in filtering, joining, and ordering.
3. Look for unnecessary full-table scans, expensive nested loop joins, and functions on columns that prevent index usage.
4. Check whether we are selecting unnecessary columns (avoid SELECT *) or processing more data than required.
5. For extremely large tables, consider table partitioning (by date/range) or read replicas.

We used distributed processing and batch-oriented approaches. Jobs were divided into manageable units and processed through queues and workers.

For database operations, we used appropriate indexing, TTL-based retention strategies, and parallel scan strategies where applicable.

We also had to think carefully about deduplication and connection management because at that scale even small inefficiencies become significant bottlenecks.

Q24. "Find the first non-repeating character in a string."

Example: "aabbcdde" → 'c'

Approach:
First count the frequency of every character using a dictionary or collections.Counter. Then iterate through the string again and return the first character whose frequency is 1.

def first_unique_char(s: str) -> str:
    counts = {}
    for ch in s:
        counts[ch] = counts.get(ch, 0) + 1
    for ch in s:
        if counts[ch] == 1:
            return ch
    return ""
Complexity: O(n) time and O(k) space, where k is the number of distinct characters (≤ 256).

Q25. "Group anagrams."

Example: ["eat", "tea", "tan", "ate", "nat", "bat"]
Expected: [["eat", "tea", "ate"], ["tan", "nat"], ["bat"]]

Answer:

from collections import defaultdict

def group_anagrams(words):
    groups = defaultdict(list)
    for word in words:
        key = ''.join(sorted(word))
        groups[key].append(word)
    return list(groups.values())

Explanation: The sorted version of each word serves as the canonical key because all anagrams produce identical sorted character sequences.

Q26. "When would you use a list, set and dictionary in Python?"

Answer:
List: Ordered collection that allows duplicates; ideal for ordered sequences and indexing.
Set: Unordered collection of unique elements with O(1) average lookup; ideal for membership testing and deduplication.
Dictionary: Key-value mapping with O(1) average lookup; ideal for caching, indexing by ID, and count aggregation.

Real Production Example: For extraction, I use a set to track already-seen product IDs for deduplication, and a dictionary to map product IDs to extracted structured payloads.

Q27. "How would you remove duplicate records from a Pandas DataFrame?"

Answer:

# Drop all exact duplicate rows
df = df.drop_duplicates()

# Drop duplicates based on a specific primary key / ID
df = df.drop_duplicates(subset=["product_id"], keep="last")

Production detail to mention: In a production pipeline, I would also decide what to do when duplicates have conflicting values — for example, sorting by timestamp and keeping the newest record rather than blindly dropping.

7. Reliability, Monitoring & System Failure Handling 4 Questions

Q12. "How do you make sure extracted data is correct?"

Answer:
I use validation at multiple levels:

1. Field Presence: Validate that mandatory fields (ID, title, price, timestamp) exist.
2. Type & Format: Prices must be numeric > 0, URLs well-formed, and IDs matching regex patterns.
3. Deduplication: Checking against database primary keys or Redis hash sets.
4. Metrics & Anomaly Detection: Monitor extraction success rates, missing-field rates, and record count trends. A sudden spike in missing fields alerts us that the target site structure changed.

Q13. "What happens if tomorrow the website changes its HTML structure?"

Answer:
That's a common and expected occurrence with web data extraction:

1. Detection: Automated monitoring flags drops in extracted record volume or sudden nulls in mandatory fields.
2. Inspection: Manually or programmatically inspect the new DOM/JSON payload.
3. Parser Update & Dual Testing: Update selectors to use resilient identifiers or switch to an internal API; verify against both old and new payload fixtures.
4. Resilience Strategy: Prefer internal APIs over HTML selectors whenever available, as APIs change less frequently than frontend markup.

Q32. "What happens if a scraper crashes halfway through 1 million records?"

Answer:
I wouldn't want the whole job to restart from zero:

1. Divide the 1 million workload into small, independent sub-tasks queued in SQS.
2. Maintain job state in the database with statuses: pending, processing, success, failed.
3. Idempotent workers ensure that re-running a task does not corrupt data.
4. SQS Visibility Timeout ensures unacknowledged tasks are re-queued to healthy workers.
5. Checkpointing ensures completed batches remain persisted so only the uncompleted portion continues.

Q33. "How do you know your scraper is working correctly?"

Answer:
I monitor both infrastructure and business-level metrics in Grafana:

Infrastructure: Worker CPU, memory usage, network I/O, queue depth, Lambda concurrency.
Extraction Domain: Accepted jobs, queued jobs, success count, failure count, and 'no worker available' states.
Quality Metrics: Success rate percentage, HTTP status code distribution (monitoring spikes in 403/429/500), and rate of empty or missing fields.

Mastering the Interviewer's Drill-Down Chain

Because your resume is very strong technically, expect the interviewer to drill down repeatedly. Here is how to navigate the classic chain:

"You used SQS."
→ Why SQS? → Decouples API ingestion from extraction worker processing and buffers traffic.
→ What happens if the worker crashes? → The visibility timeout expires without a delete call, returning the message to the queue.
→ What is visibility timeout? → The period during which SQS prevents other consumers from receiving and processing the message.
→ What happens if processing takes longer than visibility timeout? → Another worker picks up the message, producing duplicate task execution.
→ How do you prevent duplicates? → Distributed lock in Redis (SETNX with TTL) plus consumer idempotency based on unique task IDs.
→ Why Redis? → Sub-millisecond in-memory atomic operations.
→ What happens if Redis goes down? → Fallback to DB-level unique constraint or primary key conflict resolution (ON CONFLICT DO NOTHING).
→ How do you guarantee exactly-once processing? → In distributed systems, message delivery is at-least-once; true exactly-once is achieved at the destination via idempotent writes.
